# Material 3 — foundation spec

*Edition pinned: **v0.192**, context `3P / Web / Dynamic` — named in the clone's
own generated header. Measured from
`material-web/tokens/versions/v0_192/` on 2026-08-03.*

## Shape: three tiers, the most formal of the three systems

```
md.ref.*   reference palettes      76 tonal stops / 5 families
     ↓
md.sys.*   system roles            49 colour roles + 5 other subsystems
     ↓
md.comp.*  component tokens        84 token families
```

Material 3 is the only system here with a genuine component tier, and the only
one where **one of our components can be five of theirs** — button alone is
filled, outlined, text, elevated and filled-tonal.

## Tier 1 — the reference palette is a set of ramps

| family | stops |
|---|---|
| neutral | 24 |
| primary | 13 |
| secondary | 13 |
| tertiary | 13 |
| error | 13 |

Neutral carries more stops than the others because of the surface-container
ladder. The tell that these are **computed rather than chosen** is in the stop
names: alongside the round `10, 20, 30…` sit `neutral12`, `neutral17`,
`neutral22`. Nobody picks 17 by eye.

## Tier 2 — roles are positions on a ramp, not colours

All **49** colour roles resolve by pointing at a ramp stop:

```scss
'background':      map.get($deps, 'md-ref-palette', 'neutral6'),
'error':           map.get($deps, 'md-ref-palette', 'error80'),
'inverse-primary': map.get($deps, 'md-ref-palette', 'primary40'),
```

So `surface-container-high` does not mean a colour. It means *neutral at that
tone*, under this scheme, at this edition. **Colour here is the output of a
function**, and the hex values sitting in the clone are one materialisation of
it.

Five further subsystems sit at the same tier, each its own file:
`elevation`, `motion`, `shape`, `state`, `typescale`.

## Tier 3 — 84 component token families

One file per component-and-variant. This is where M3 is easiest to read and most
dangerous to trust: the values are right there, fully resolved, which makes it
tempting to copy them without recording *which computation produced them*.

## Why the edition is pinned

Because tier 1 is generated. A value that is computed rather than authored can
move between editions without anyone editing a file — so **"Material 3 says X"
is meaningless without naming the edition that computed it.** Every M3 column in
this registry is pinned to `v0.192`, and that pin is checked.

## The structural consequence for this registry

M3 has **51 semantic colour roles no second system has** (the surface-container
ladder, fixed roles, inverse roles). Our own anti-retrofit rule — *no semantic
slot without proof across two or more systems* — would have barred all of them
from the shared contract forever, forcing their values into per-component
switches and destroying sparse overrides for every container-shaped component.

The fix was **adapter-private semantic namespaces**: M3 may declare
`x-m3-surface-container-high` one level above its component switches, resolvable
only inside its own fallback chains. The shared contract stays lean; M3 keeps its
full vocabulary. See [`../DISCOVERY.md`](../DISCOVERY.md) § the flaw the stress
test caught.

## How a registry slot cites into this

```json
"action": "#6750a4"
"provenance": { "action": "_md-sys-color.scss 'primary' -> md-ref-palette 'primary40'" }
```

The citation names **both** tiers, because naming only the hex would lose the
one fact that matters — that the value is a ramp position, not a choice.

## Structure and behaviour are inferred, not read

`material-web` is a tokens-only clone. There is no component source, so **every
M3 `structure` and `behavior` cell in this registry is `[R]`** — inferred from
the published spec — and only `style` cells are `[S]`.

That is not a formality. **Three of the twenty-one `[R]` cells in the calendar
were wrong.** `[R]` is a debt, not a citation.
